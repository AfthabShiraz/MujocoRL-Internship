## 11 -- AnyRotate and Text2Touch: verdict

**Overall:** AnyRotate/Text2Touch support the current reward-equilibrium account, refine `01-INTERIM` on the gate variable, and do not rescue the already-failed "just make success bigger" fix. The closest AnyRotate analogue to our local optimum is not a missing contact reward; it is our conservative penalties being live at full weight from step 1 while success is only 0.03-0.05 goals/episode. The source supports `01-INTERIM` that `action_rate` is the first cost-side suspect: logged stall costs are `action_rate = -0.44/s` versus `hand_pose = -0.11/s`, so the initial curriculum floor should remove or sharply reduce `action_rate` first, not gently ramp all costs together. AnyRotate's `d_tol` ablation is the cleanest bootstrap lead here: 0.15 -> 0.25 gives 0.75 -> 1.77 rotations/episode and 3.07 -> 5.26 successes. Our only threshold-relaxation run is run 2, but it bundled threshold 0.1 -> 0.4 with four other changes on the pre-fix model, so it is a confound, not evidence against relaxed tolerance.

### Mapping AnyRotate's penalty curriculum onto our reward

AnyRotate's gated terms are `r_contact = lambda_rew (...)` and `r_stable = lambda_rew (...)`, with `lambda_rew = (g_eval - 1.0)/(2.0 - 1.0)`; it explicitly warns those terms can induce a stable-grasp/minimal-rotation local optimum. In our reward, the direct analogues are:

| Our term | Weight | AnyRotate analogue | Verdict |
|---|---:|---|---|
| `hand_pose` | -0.5 | `lambda_pose r_pose` | conservative pose prior; gate it |
| `action_rate` | -0.001 | no exact term, but same stability/conservative-motion role as low-work/low-torque/low-velocity shaping | gate it first; it dominates |
| `energy` | -1e-3 | `lambda_work`, `lambda_torque` | gate it, but current magnitude is not logged |
| `termination` | -100 | `r_terminate`, not multiplied by `lambda_rew` in AnyRotate | do not map into the conservative curriculum by default |

This supports `01-INTERIM`'s "action_rate is dominant" claim: the measured cost at the stall is `action_rate -0.44/s`, `hand_pose -0.11/s`, and energy unlogged; `action_rate` is 4x `hand_pose` and no run has varied its weight. It refines `01-INTERIM` by saying an AnyRotate-style curriculum should start with `action_rate` at 0.0, `hand_pose` at 0.0 or at most a small floor, and `energy` at 0.0 until bootstrap successes exist. A 25% floor on `action_rate` would already be about `-0.11/s`, equal to current `hand_pose`; a 100% floor is exactly the current failure setting.

The gate-variable problem is decisive. AnyRotate's gate starts at 1.0 goals/episode; our fixed-model success rate is 0.03-0.05 goals/episode and run 20 confirms 0.0287 after the counter fix. A literal port would set `lambda_rew < 0` unless clamped, i.e. clamped to 0 forever. That is not our current situation: our conservative penalties are full-weight from step 1. The correct mjlab gate is an EMA of our own `goals_reached`/episode or deterministic success fraction under the current command, but with thresholds matched to our bootstrap regime, not AnyRotate's solved-policy regime. Concretely: `lambda_cons = clamp((ema_goals - 0.05) / (0.25 - 0.05), 0, 1)` for a first probe, or gate on a relaxed auxiliary/tolerance success signal if `d_tol` is being tested. Hooking it in mjlab is straightforward: add a reward helper in `rewards.py` that computes the base penalty and multiplies by a curriculum scalar stored on the `goal_orientation` command or updated by a `CurriculumTermCfg`; then replace the static `hand_pose`, `action_rate`, and `energy` RewardTermCfg functions in `env_cfg.py` with scaled versions. The existing `goal_difficulty` curriculum already lives in `env_cfg.py`, with `promote_at`, `demote_at`, `update_every`, and EMA parameters, so the right hook point exists.

### Keypoint versus quaternion error

Our current quaternion-angle kernel is linear down to 0.2 rad, then flat. At weight 5, its marginal value is `5/pi = 1.592/rad = 0.0278/deg` from 180 deg to 11.5 deg, then exactly 0 below 11.5 deg. The interim inverse-kernel recommendation, weighted at 8.93 to match the linear slope at 130 deg, has marginal value `8.93/(err+0.1)^2`: 0.4009/deg at 30 deg, 3.9173/deg at 5.7 deg, and 13.1865/deg at 0.5 deg. That is the only compared kernel here with monotonically increasing pull all the way to the goal.

AnyRotate's six-keypoint distance is a different object. With keypoints at radius `R = 0.05 m`, a small rotation vector `w` moves keypoint `p` by `|w x p|`. For the six axis keypoints, mean keypoint distance near zero is:

`d_kp(w) = (R/6) * sum_i sqrt(|w|^2 - w_i^2)`.

For rotation about a cube principal axis, `d_kp ~= (2/3)R|w| = 0.0333|w| m`; for an equal-component axis, `d_kp ~= 0.0408|w| m`. So the keypoint metric has a finite, geometry-dependent local slope, about 22% larger for diagonal-axis error than principal-axis error. It is not singular like `1/(err+eps)`, and unlike our current linear kernel it need not go dead inside 0.2 rad unless the reward wrapper saturates there. Because the analysis file gives the AnyRotate keypoint formula but not enough unambiguous sign/units to recover an exact reward-per-degree at zero, the exact marginal reward value for their keypoint kernel is OPEN; the geometric distance slope is DONE.

This refines the kernel interim. A keypoint-distance kernel would not simply be "the inverse kernel with keypoints." It changes the error geometry and removes the raw quaternion angle's axis blindness, but it does not obviously solve our 96% tip-over residual. Raw quaternion angle treats a 10 deg spin and a 10 deg tip as equal. Six keypoints also treat rotations geometrically, but for a symmetric cube-face keypoint set the near-goal spin/tip difference is mostly an axis-dependent rescale, not a targeted tip-over bonus. Since our residual is 96% tip-over, switching to keypoints might slightly change the measured spin/tip decomposition, but the source does not support claiming it will turn tip-over into an easier objective. Prediction: keypoints alone will mostly rescale the same equilibrium unless paired with a near-goal kernel or relaxed tolerance.

Evidence: current kernel code is `quat_error_magnitude` plus `_linear_tolerance` in `leapXelaMjLab/src/leap_xela_mjlab/tasks/reorient/mdp/rewards.py:21`-`46`; the marginal table for linear, long-tail, and inverse is in `research/verdicts/00-INTERIM-reward-kernel.md:30`-`53`; AnyRotate's keypoint constants are in `research/analysis/11-anyrotate-and-text2touch-reward-ablations.md:46`-`50`; our tip-over residual is recorded at `leapXelaMjLab/TRAINING_NOTES.md:517`-`536` and deterministic run-14 eval reports spin 93.5% versus tip 66.9% at `leapXelaMjLab/eval/run14_iter1500_eval.txt:228`-`231`.

### Ranked recommendation

1. Run `1/(err+0.1)` orientation kernel at the 00-INTERIM matched-slope weight first. It is the cleanest worth-of-precision test and directly attacks the dead/flat near-goal marginal profile.
2. In parallel or next, run `action_rate=0` or a conservative-term curriculum starting with `action_rate=hand_pose=energy=0`, `termination=-100`. Use an EMA gate calibrated to 0.05 -> 0.25 goals/episode, not AnyRotate's 1.0 -> 2.0.
3. Run a clean relaxed-tolerance bootstrap test. Do not cite run 2 either way.
4. Defer keypoint distance until after an offline gradient audit. It is geometrically interesting, but the corpus supports "different rescaling" more than "tip-over fix."
5. Do not repeat run 20. Text2Touch's lesson is scalable sparse terms inside a reachable, bounded reward design process; our 20x success multiplier was already tested and was harmful.
