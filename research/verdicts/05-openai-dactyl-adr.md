## 05 -- OpenAI Dactyl and ADR: verdict

**Overall:** OpenAI Dactyl/ADR supports the broad diagnosis that this task needs reachable sparse success and goal-level pressure, but it does **not** support the headline reward swap as written. A pure `d_t - d_{t+1}` progress term has constant marginal value per radian, telescopes to `d_0 - d_T`, and therefore predicts a null on the same equilibrium mechanism that explains the current 25-30 deg stall. The actionable residue is not "copy Dactyl reward"; it is: test a clean 0.4 rad bootstrap, test a per-goal timeout/resample mechanism, and treat ADR/recurrent policies as expensive curriculum/adaptation levers only after the reward/time-limit issue is separated.

### Is progress shaping actually different from our linear kernel?

Let `d_t` be the geodesic angular error in radians at control step `t`. The current orientation term is implemented as `cube_orientation_tolerance`, which computes `err = quat_error_magnitude(...)` and then `_linear_tolerance(err, bounds=(0, 0.2), margin=pi)` ([rewards.py](/Users/afthabshiraz/Desktop/MujocoRL-Internship/leapXelaMjLab/src/leap_xela_mjlab/tasks/reorient/mdp/rewards.py:21), [rewards.py](/Users/afthabshiraz/Desktop/MujocoRL-Internship/leapXelaMjLab/src/leap_xela_mjlab/tasks/reorient/mdp/rewards.py:35)). For `d > 0.2`, the raw kernel is

`L(d) = 1 - (d - 0.2) / pi`.

With orientation weight `w = 5`, the per-second reward contribution before other terms is

`R_abs(d) = w L(d) = 5 - (5/pi)(d - 0.2)`.

So its marginal value for reducing error is constant:

`dR_abs/dd = -5/pi`, therefore `-dR_abs/dd = 5/pi = 1.5915 reward/rad = 0.0278 reward/deg`.

That supports 00-INTERIM and the current equilibrium account: the reward pays the same extra `0.0278` per degree at 130 deg and at 30 deg, while the manipulation cost of the next degree plausibly rises near the goal. Below `0.2 rad = 11.46 deg`, `L(d)=1`, so the orientation term's marginal value is exactly zero; the only pull from 11.46 deg to the configured `0.1 rad = 5.73 deg` success threshold is the sparse success bonus ([rewards.py](/Users/afthabshiraz/Desktop/MujocoRL-Internship/leapXelaMjLab/src/leap_xela_mjlab/tasks/reorient/mdp/rewards.py:225)).

Dactyl's dense term is stated in 05 as

`R_prog,t = k (d_t - d_{t+1})`.

For a small improvement `Delta = d_t - d_{t+1} > 0`,

`R_prog,t = k Delta`, so `partial R_prog,t / partial Delta = k`.

That marginal value per radian of error reduction is also constant. It does not become more valuable near the goal. It is the temporal difference of the potential `Phi(s) = -k d(s)`:

`R_prog,t = Phi(s_{t+1}) - Phi(s_t) = -k d_{t+1} - (-k d_t) = k(d_t - d_{t+1})`.

For a fixed transition, this is algebraically different from paying `R_abs(d_t)`, because parking at a fixed nonzero `d` earns zero progress instead of a dense holding reward. But for the crux in this codebase, "what is one more degree worth?", the answer is the same: constant `k` per radian. If the stall is an equilibrium where constant marginal angular value meets rising marginal precision cost, swapping the current absolute linear kernel for a **pure** potential-based progress term should reproduce the same equilibrium location up to scale. It predicts a null result, not a positive reward-shape fix.

The telescoping property makes that sharper. Over one uninterrupted goal attempt:

`sum_{t=0}^{T-1} (d_t - d_{t+1}) = (d_0 - d_1) + (d_1 - d_2) + ... + (d_{T-1} - d_T) = d_0 - d_T`.

With weight `k`, total dense progress return is `k(d_0 - d_T)`. The path shape cancels. A fast clean path, a slow dithering path, and a path that overshoots and comes back get the same progress contribution if they start and end at the same error, ignoring discount and clipping. This is exactly what the local `orientation_progress` class says in code: it pays `prev_err - err` and notes that it "telescopes over an episode to the total progress made" ([rewards.py](/Users/afthabshiraz/Desktop/MujocoRL-Internship/leapXelaMjLab/src/leap_xela_mjlab/tasks/reorient/mdp/rewards.py:128), [rewards.py](/Users/afthabshiraz/Desktop/MujocoRL-Internship/leapXelaMjLab/src/leap_xela_mjlab/tasks/reorient/mdp/rewards.py:164)).

That telescoping interacts badly with the current lack of a per-goal timeout. The command tracks `steps_since_last_success`, but only as a metric; it is incremented in `_update_metrics` and never used for termination or goal failure ([commands.py](/Users/afthabshiraz/Desktop/MujocoRL-Internship/leapXelaMjLab/src/leap_xela_mjlab/tasks/reorient/mdp/commands.py:143)). The MDP termination file defines only `cube_fell_below`; the environment adds global `time_out` and `nan`, but there is no per-goal failure term ([terminations.py](/Users/afthabshiraz/Desktop/MujocoRL-Internship/leapXelaMjLab/src/leap_xela_mjlab/tasks/reorient/mdp/terminations.py:15)). Therefore, with pure progress and no per-goal timeout, an episode that moves from 130 deg to 30 deg in 10 s and parks for the remaining 40 s receives the same undiscounted progress return as one that moves from 130 deg to 30 deg in 50 s. Once it reaches the equilibrium shell, extra waiting is almost free under progress itself; the only remaining pressure comes from other rewards/penalties and global episode discounting. Worse, if the policy cannot cross the sparse threshold, the task has no mechanism that says "this goal attempt failed; stop paying attention to it."

With a per-goal timeout, the same telescoping term becomes less perverse because `T` is bounded per target. A timeout converts "park forever at 30 deg" into a failed attempt after a fixed horizon, and a Dactyl-style timeout that marks the goal failed and resamples a new goal changes the data distribution: the policy gets many bounded goal attempts per episode instead of one long parked attempt. That is meaningfully different from simply terminating the whole episode. Dactyl-style fail+resample preserves the hand/cube state, avoids making timeout identical to drop, and trains recovery plus repeated goal attempts from in-hand states. Episode termination resets the whole state and, with the current `termination` reward of `-100`, risks teaching "avoid hard attempts" rather than "move on to the next goal." The distinguishing evidence in this codebase would be a two-cell test: timeout-fail+resample versus timeout-terminate, same horizon and reward weights. If fail+resample increases attempts per episode and deterministic 0.4/0.1 rad success without shortening episodes, while terminate mainly shortens episodes or raises drop/timeout penalties, the mechanisms are different. If both produce the same best-error and success curves, then the simpler terminate variant is enough.

Existing results sharpen the verdict rather than replace the algebra. Run 22 pinned one goal for the full episode (`--goal-drift False --goal-resample-on-success False`) and got much worse: about 77 deg best/final error versus about 33 deg for baseline under the matched pinned-goal measurement, and the JSON here reports 79.25 deg best with 0/32 successes. That supports 01-INTERIM's claim that goal refresh pressure matters, but it does **not** prove Dactyl-style timeout; it proves the no-refresh single-goal regime is bad. Run 23 added a peaked `orientation_fine` long-tail term beside the linear term and was worse: 64 deg versus 37 deg at matched iteration 600, 0/32 successes. That invalidates the "bolt a fine term beside the linear term" variant, but not a clean replacement kernel. Run 2 moved success threshold from 0.1 to 0.4 rad, but it also added `orientation_fine`, changed orientation weight 5 to 1, lowered `init_std`, and lowered entropy on the pre-fix broken model, so it is not a clean threshold test.

A clean isolated 0.4 rad bootstrap test is simple: start from the clean run-14/run-24 fixed model, vary only `orientation_success_threshold: 0.1 -> 0.4`, leave reward weights, goal drift/resampling, entropy, orientation kernel, contact settings, and batch shape unchanged, train to 1500 iterations, and score with deterministic eval at both 0.4 rad and 0.1 rad. The bootstrap framing is supported only if the relaxed run produces many deliberate 0.4 rad goal hits early, resamples goals repeatedly, and then after tightening to 0.1 rad beats baseline terminal precision. A concrete bar: by 1500 iterations, deterministic held or settled success at 0.4 rad should be comfortably nonzero, and the tightened/evaluated policy should move below the current 24.8-28.9 deg best-error band or produce nonzero held successes at 0.1 rad. It is disproved if it merely increases noisy training-time threshold crossings while deterministic best error and held/settled success remain in the current band.

### Still open from this source

- OPEN / WORTH: clean `0.4 rad` bootstrap threshold test. Cost: one threshold-only run plus one tighten/eval continuation. It must create deterministic 0.4 rad held/settled success and then improve 0.1 rad performance, or it is just moving the scoreboard.
- OPEN / TASK-DISTRIBUTION: per-goal timeout, explicitly comparing Dactyl-style fail+resample against terminate-on-timeout. Cost: two matched 1500-iteration runs after a small code change.
- OPEN / TASK-DISTRIBUTION: fixed-model reachable-goal curriculum or no-randomization bootstrap before full ADR. Cost: one to two runs. It must beat the 24.8-28.9 deg deterministic band by more than the 3 deg floor.
- OPEN / TASK-DISTRIBUTION: minimal ADR-style randomization ramp only if the calibrated/no-DR run first shows sparse successes. Cost: two to four runs plus scheduler work.
- OPEN / COST: recurrent policy. Cost: architecture work plus at least two runs. It needs a large quantitative win, not a cosmetic reward increase.
- OPEN / COST: 80 ms/smoothed action ablation. Cost: one run, low priority because action-magnitude fixes already failed to move success.
- OPEN / TASK-DISTRIBUTION: restricted face-up/upward goal distribution as a capability probe. Cost: one run; it changes the task, so treat it as diagnosis, not final optimization.

### Ranked recommendation

1. Run the clean `0.4 rad` bootstrap test first. It is the cheapest way to decide whether Dactyl's tolerance matters as curriculum rather than as a permanent easier task, and Run 2 is unusable because it bundled four other changes.
2. Implement per-goal timeout as fail+resample and run it against a terminate-on-timeout variant. This is the part of Dactyl that actually changes the parking incentive; it directly refines 01-INTERIM instead of repeating it.
3. Do a calibrated/no-randomization bootstrap run before building ADR. If the policy cannot beat 25-30 deg in a single easy environment, ADR is expensive theater.
4. If and only if the calibrated run works, add a minimal ADR ramp over existing randomization fields. The source supports gradual expansion after success, not full fixed entropy from step one.
5. Defer recurrence until the threshold/timeout/curriculum tests are done. LSTM is plausible under randomization, but it is a costly architecture lever and not a clean explanation for the current constant-marginal reward shell.
6. Do not run pure `d_t - d_{t+1}` as the next reward fix. The algebra predicts a null; the reward-shape experiment worth running is a genuinely increasing near-goal marginal value, not potential-based progress alone.
