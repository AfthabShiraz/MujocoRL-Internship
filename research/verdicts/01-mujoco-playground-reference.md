## 01 -- MuJoCo Playground reference: verdict

**Overall:** This source is mostly spent as a port-parity/debug source. It strongly supported the 2026-09-06 parity audit: the mjlab port matches playground on actor obs 57, critic obs 91, `history_len=1`, obs noise, reward scales, orientation kernel, actuators, cube geometry, and goal drift; the only real implementation deviation was the dt-scaled success bonus, and run 20 showed that fixing it was harmful (`orientation_error` 0.74 -> 1.10, std 2.06 -> 5.95, success still 0.0287). What remains load-bearing is not "find the port bug"; it is the paper-vs-code task gap: the paper describes stuck termination and >=90 deg target jumps, while the playground code and this faithful port implement neither.

### Paper-versus-code gaps

The 30 s stuck termination is real in the paper and absent from the playground code. The paper says episodes continue until the cube is dropped or the hand is stuck for over 30 s (`mujoco_playground_paper__arxiv_2502.08844.txt:3667-3673`). Playground code increments `steps_since_last_success` (`repo_mujoco_playground_leap_hand.txt:239-250`) but `_get_termination` ignores it and returns only cube fall or NaN (`repo_mujoco_playground_leap_hand.txt:290-294`). The mjlab port faithfully reproduces that omission: `steps_since_last_success` is a metric in `commands.py:63-70,143-147`, while terminations are only `time_out`, `cube_fell`, and `nan` (`env_cfg.py:426-434`; `terminations.py:15-23`). This supports the interim open-lever verdict at `01-INTERIM-open-levers.md:74-107`: matching the reference implementation and matching the reference task diverge here.

Other paper-vs-code divergences found in this source: the paper says new orientations are sampled at least 90 deg away (`mujoco_playground_paper__arxiv_2502.08844.txt:3667-3673`), but the code applies a smooth `goal_quat_dquat` kick/decay and integrates the existing mocap quaternion (`repo_mujoco_playground_leap_hand.txt:261-275`), matched by mjlab (`commands.py:195-208`). The paper says actor observations include noisy hand joint positions and velocities (`mujoco_playground_paper__arxiv_2502.08844.txt:3677-3687`), but playground actor state has joint angles, qpos error history, cube position/orientation error history, and last action only; velocities are critic-only (`repo_mujoco_playground_leap_hand.txt:374-393`), and mjlab matches that (`env_cfg.py:128-184`). The paper describes 200M pretraining plus 100M fine-tuning with random pose injection and torque limits (`mujoco_playground_paper__arxiv_2502.08844.txt:3691`), while the code config for `LeapCubeReorient` is a single 200M run (`repo_mujoco_playground_leap_hand.txt:1886-1903`) and default random pose injection is 0.0 (`repo_mujoco_playground_leap_hand.txt:63-70`). The paper table extraction is internally inconsistent/noisy in the local text dump around Table XXX (`mujoco_playground_paper__arxiv_2502.08844.txt:5614-5648`), so I do not treat its sample-budget table as cleaner than the code.

### Still open from this source

Three things survive. First, the paper-task per-goal timeout: terminate, not time-out, when `steps_since_last_success > 600` at 20 Hz. This changes the task/state distribution by removing the value of parking, not the cost of precision or the reward worth of the last degree; cost is one run, about 100 min; prediction is more early terminations and higher variance, with success only meaningful if deterministic best error leaves the 24.8-27.1 deg / 0/32 band.

Second, a clean relaxed-success probe at 0.2 or 0.4 rad on the fixed model. This changes task/state distribution and worth together, so it is diagnostic rather than a clean fix; cost is one run plus strict-threshold eval/fine-tune; prediction is early `success_count` if sparse bootstrapping is the issue, but no strict transfer if the policy merely learns the easier task.

Third, the narrow finger-pad rolling claim on curved phalanges. The palm rolling probe is null: pads 0.2114 N m breakaway vs smooth 0.2140 N m, equal/lower running torque (`TRAINING_NOTES.md:1892-1913`), but the finger rig failed because the curved pad track slid/tumbled (`TRAINING_NOTES.md:1915-1920`). This is a cost-of-precision/contact-mechanics question, not the main explanation unless it predicts a metric outside the established null band.

### Ranked recommendation

1. Run the reward-kernel test from `00-INTERIM`: replace the linear orientation kernel with `1/(err+0.1)` at weight about 8.9. It changes what precision is worth, and its falsifiable prediction is total closure leaving 77.6-81.4% rather than rebalancing (`00-INTERIM-reward-kernel.md:89-109`).
2. Run `action_rate` weight -> 0. It is the dominant logged cost term and has never been varied; it tests whether the equilibrium account is too dismissive of non-physical reward costs (`01-INTERIM-open-levers.md:11-70`).
3. Run the paper-task timeout at 600 steps since last success. This is the sharpest reference-task gap: code parity is already closed, but task parity is not.
4. Run the symmetry-reduced error only as a capability probe, not as reference matching. It changes the task/state distribution; success would show the hand can do terminal precision on easier goals, failure would reopen capability limits (`01-INTERIM-open-levers.md:110-148`).
5. Only after those, consider the clean relaxed-success probe or curved-finger rolling rig. Both are diagnostic; neither should outrank the reward/action-rate/task-gap tests.
