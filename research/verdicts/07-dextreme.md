## 07 -- DeXtreme: verdict

**Overall:** the 00-INTERIM kernel recommendation does **not** stand as-is. The shape survives: DeXtreme and the interim marginal table both support replacing the current linear/flat orientation term with a monotone near-goal kernel. The prescription "1/(d+0.1) at weight about 8.9, keep everything else fixed" is too aggressive for this stack: it raises the dense term from about 3.8 at 130 deg to about 82 at 0.5 deg before dt scaling (`research/verdicts/00-INTERIM-reward-kernel.md:32-43`), while this RSL-RL config has only observation normalization, `gamma=0.99`, and no value-normalization setting in `rl_cfg.py` (`leapXelaMjLab/src/leap_xela_mjlab/tasks/reorient/config/rl_cfg.py:27-55`). Revised recommendation: try the inverse kernel only with explicit numeric guardrails -- value/return normalization if available, or a capped/ramped kernel -- and do **not** combine it with a DeXtreme-sized success bonus in the first run, because this project's 20x success-bonus test already failed hard (`leapXelaMjLab/TRAINING_NOTES.md:724-763`).

### Pressure-testing the 1/(d+eps) recommendation

#### 1. Kernel alone vs. kernel plus DeXtreme's large success bonus

DeXtreme's reported reward uses `1 / (d + 0.1)` at weight `1.0` and a reach-goal bonus of `250.0` when `d < 0.1` (`research/analysis/07-dextreme.md:20-27`). This project currently leaves the success weight at `100.0` inside a dt-scaled reward manager, so the effective one-step bonus is `100 * 0.05 = 5`; the code documents the discrepancy directly (`leapXelaMjLab/src/leap_xela_mjlab/tasks/reorient/config/env_cfg.py:361-383`) and sets `scale_rewards_by_dt=True` with `episode_length_s=50.0` (`leapXelaMjLab/src/leap_xela_mjlab/tasks/reorient/config/env_cfg.py:504-508`).

Run 20 is the key local evidence. It changed success weight `100 -> 2000` to cancel dt scaling (`leapXelaMjLab/TRAINING_NOTES.md:724-733`) and was harmful: reward fell `143.60 -> 75.05`, action std rose `2.06 -> 5.95`, final `orientation_error` was `1.0998`, and success stayed `0.0287`, inside the same flat `0.03-0.05` band (`leapXelaMjLab/TRAINING_NOTES.md:737-763`). That invalidates "just restore the big sparse bonus" locally. It does **not** invalidate the inverse dense kernel, because run 20 kept the old linear/flat orientation reward; the attempted pair was not actually DeXtreme's pair.

The large bonus does not look load-bearing for the dense kernel's gradient: `1/(d+0.1)` itself keeps increasing all the way to zero error, unlike the current tolerance term which is flat below `0.2` rad (`leapXelaMjLab/src/leap_xela_mjlab/tasks/reorient/mdp/rewards.py:35-46`; `research/verdicts/00-INTERIM-reward-kernel.md:20-28`). But DeXtreme's full reward stack also includes direct PD target actions, EMA smoothing, an LSTM policy, broader ADR, and a different simulator (`research/analysis/07-dextreme.md:40-88`, `research/analysis/07-dextreme.md:155-171`), so copying the bonus/kernel package is not a clean transfer.

Verdict: 00-INTERIM is **refined, not dropped**. Try the inverse dense kernel without increasing the success bonus first; if someone proposes "inverse kernel plus DeXtreme-sized bonus" as the next run, revise it down or stage it later, because the only local large-bonus test was harmful.

#### 2. Value scale, normalization, and gamma

The prompt says DeXtreme used value normalization, but the DeXtreme analysis file read for this verdict does **not** verify that. It says "number of minibatches, advantage normalization, value normalization, value clipping ... not reported" and reports only "Policy preprocessing: subtract mean and divide by standard deviation" (`research/analysis/07-dextreme.md:81-83`); the notable summary also lists "value normalization" under "Not reported in this source" (`research/analysis/07-dextreme.md:225`). So this verdict cannot cite DeXtreme value normalization as a fact from the assigned source.

This project does have empirical **observation** normalization: `rl_cfg.py` sets `obs_normalization=True` for both actor and critic (`leapXelaMjLab/src/leap_xela_mjlab/tasks/reorient/config/rl_cfg.py:27-41`), and eval output shows `EmpiricalNormalization()` inside both actor and critic models (`leapXelaMjLab/eval/run14_iter1500_eval.txt:177-200`). I found no value-normalizer or return-normalizer setting in `rl_cfg.py`; the PPO config has `value_loss_coef=1.0`, `use_clipped_value_loss=True`, `clip_param=0.2`, and `gamma=0.99` (`leapXelaMjLab/src/leap_xela_mjlab/tasks/reorient/config/rl_cfg.py:42-55`). DeXtreme's `gamma` is `0.998`, but the same analysis says that higher discount was essential for training LSTMs (`research/analysis/07-dextreme.md:66-67`), while this project uses 512-256-128 MLPs (`leapXelaMjLab/src/leap_xela_mjlab/tasks/reorient/config/rl_cfg.py:27-40`) and `history_length=1` (`leapXelaMjLab/src/leap_xela_mjlab/tasks/reorient/config/env_cfg.py:186-200`).

The numeric risk is real. 00-INTERIM's matched-slope weight makes the raw inverse reward about `3.77` at 130 deg and `82.15` at 0.5 deg (`research/verdicts/00-INTERIM-reward-kernel.md:35-43`). With `scale_rewards_by_dt=True`, those are still large, sharply state-dependent per-step rewards once multiplied by `0.05`, and the critic has no explicit value normalization in the local config.

Verdict: 00-INTERIM as a pure single-variable change is **numerically unsafe**. Companion change should be value/return normalization if RSL-RL exposes it; otherwise cap or ramp the inverse reward and set a critic-loss/NaN abort criterion. Do **not** change `gamma` to `0.998` in the same run unless also moving to an LSTM, because the assigned DeXtreme analysis ties `0.998` to LSTM training, not to the reward kernel alone.

#### 3. Action smoothing vs. the 01-INTERIM action_rate-to-zero proposal

DeXtreme is pointed in the opposite direction from "set action_rate to zero." It uses an action-delta penalty `||targ_curr - targ_prev||^2` at weight `-0.25`, EMA smoothing annealed `0.2 -> 0.15` during training, and `0.1` for the best real-robot results (`research/analysis/07-dextreme.md:23-49`). The source-grounded purpose matters: the analysis says EMA tuning was useful for "speed, agility, stability, and hardware protection" (`research/analysis/07-dextreme.md:46-49`) and frames DeXtreme as a sim-to-real system (`research/analysis/07-dextreme.md:12-16`).

This project's action term is different. Actions are relative/integrating delta joint-position targets with `scale=0.5`, `clip_to_ctrl_limits=True`, and `ema_alpha=1.0`, where `1.0` disables smoothing (`leapXelaMjLab/src/leap_xela_mjlab/tasks/reorient/config/env_cfg.py:203-212`; `leapXelaMjLab/src/leap_xela_mjlab/tasks/reorient/mdp/actions.py:75-84`). Its `action_rate_l2` is not exactly DeXtreme's target-delta penalty: it penalizes both first and second differences of the raw policy action (`leapXelaMjLab/src/leap_xela_mjlab/tasks/reorient/mdp/rewards.py:106-125`) at weight `-0.001` (`leapXelaMjLab/src/leap_xela_mjlab/tasks/reorient/config/env_cfg.py:343-346`). 01-INTERIM's reason for zeroing it is local and quantitative: the logged `action_rate` contribution is about `-0.44/s`, roughly 4x `hand_pose`, and no run has varied that weight (`research/verdicts/01-INTERIM-open-levers.md:11-57`).

So DeXtreme does argue against making `action_rate=0` the new default, but it does not kill the ablation. The analogy is weakened by different action semantics and by DeXtreme's sim-to-real/hardware-protection objective. It is also weakened by the fact that local action-magnitude penalties already reduced action magnitude 2.6x/6x without solving the stall: run 27 was worse, run 28 was only an n=1 hint, and both had `0/32` successes (`leapXelaMjLab/TRAINING_NOTES.md:1573-1639`; `leapXelaMjLab/eval/action-l2-1e3_eval.txt:218-247`; `leapXelaMjLab/eval/action-l2-1e4_eval.txt:218-247`).

Verdict: DeXtreme **moderately contradicts** 01-INTERIM if the proposal is "remove action-rate pressure as a production setting." It only **weakly contradicts** a one-run diagnostic at `action_rate=0`, because that test targets a local reward-cost hypothesis DeXtreme did not isolate.

#### 4. Train/test threshold mismatch and what to report here

DeXtreme explicitly has both thresholds in the assigned analysis: reward/training success at `d < 0.1`, but testing/reporting at `0.4` rad (`research/analysis/07-dextreme.md:14-16`, `research/analysis/07-dextreme.md:30-36`). This project also has multiple thresholds, but by preset: the command threshold and success reward threshold are `0.1` for `baseline/reference` and `0.4` for the non-baseline curriculum preset (`leapXelaMjLab/src/leap_xela_mjlab/tasks/reorient/config/env_cfg.py:215-228`, `leapXelaMjLab/src/leap_xela_mjlab/tasks/reorient/config/env_cfg.py:361-388`). The reference runs that matter here are registered with `preset="reference"` (`leapXelaMjLab/src/leap_xela_mjlab/tasks/reorient/config/__init__.py:26-33`), which maps to the baseline/reference training settings in `rl_cfg.py` (`leapXelaMjLab/src/leap_xela_mjlab/tasks/reorient/config/rl_cfg.py:20-25`).

The eval tool already separates the reporting threshold from the env's own goal-drift trigger: `success_threshold` defaults to `0.1` and is documented as "Reporting threshold only" (`leapXelaMjLab/scripts/eval_policy.py:65-78`). It also reports instantaneous, held, and settled success (`leapXelaMjLab/scripts/eval_policy.py:338-350`, `leapXelaMjLab/scripts/eval_policy.py:418-425`). Existing deterministic eval JSONs in `eval/` were written with `success_threshold_rad: 0.1`; for example run 14 records `0.1`, 32 episodes, median best error `25.59` deg, and `n_success: 0` (`leapXelaMjLab/eval/run14_det.json:1-18`, `leapXelaMjLab/eval/run14_det.json:28-66`), while run 28 records `0.1`, median best error `22.44` deg, and `0` instantaneous/held/settled successes (`leapXelaMjLab/eval/action-l2-1e4_det.json:1-23`, `leapXelaMjLab/eval/action-l2-1e4_det.json:35-77`).

The DeXtreme-style `0.4` rad report is still useful, but only as a coarse diagnostic. `0.4` rad is 22.9 deg, which is right at this project's best deterministic medians: run 14 is `25.6` deg and run 28 is `22.4` deg (`leapXelaMjLab/eval/run14_det.json:28-36`; `leapXelaMjLab/eval/action-l2-1e4_det.json:35-43`). Reporting only `<0.1` rad says "terminal precision failed"; adding `<0.4` rad would show whether a run crosses DeXtreme's easier reported test band. It must be labeled clearly so it is not mistaken for this project's training success criterion.

Verdict: threshold-mismatch reporting is **partly handled** by `eval_policy.py`, but the stored eval artifacts are still `0.1`-only. Future verdict tables should report both `<0.1 rad` and `<0.4 rad`, plus held/settled variants, with `<0.1 rad` remaining the headline for reference-task success.

### Still open from this source

- Whether `1/(d+0.1)` works in this RSL-RL/MuJoCo Warp stack with a capped/ramped value scale and the existing effective success bonus of 5.
- Whether value or return normalization is available in mjlab/RSL-RL here; `rl_cfg.py` exposes observation normalization but no value-normalization field.
- Whether action smoothing helps local terminal precision or only helps the sim-to-real/hardware-protection objectives DeXtreme cared about.
- Whether reporting `<0.4 rad` changes prioritization: current `<0.1 rad` evals are all 0/32, but some runs sit near the 22.9 deg coarse threshold.
- Whether an LSTM plus longer-credit PPO is worth its cost after cheaper reward-shape and action-rate diagnostics.

### Ranked recommendation

1. **[WORTH] Run inverse orientation kernel only with numeric guardrails.** Implement `1/(d+0.1)` as a replacement, not an added term, but cap/ramp it or enable value/return normalization first; keep success weight at 100. Cost: 1 run plus a small reward/config edit.
2. **[TASK-DISTRIBUTION] Add `<0.4 rad` to eval reporting for every existing and future checkpoint.** Keep `<0.1 rad` as the headline, but report DeXtreme's coarse threshold and held/settled variants. Cost: no training.
3. **[COST] Run `action_rate=0` once as a diagnostic, not a new default.** DeXtreme moderately argues against removing smoothness pressure, but the local cost-side hypothesis deserves one clean test. Cost: 1 run.
4. **[COST] Expose EMA smoothing and test one conservative value before a grid.** Start with a single EMA setting near DeXtreme's training range rather than copying its whole target-delta stack. Cost: 1 run for the scout, 2 more only if it moves.
5. **[WORTH] Defer LSTM/`gamma=0.998` until after the reward-kernel and action-rate diagnostics.** It is the closest DeXtreme architectural match, but it is a high-cost stack change and should not be bundled with the kernel.
